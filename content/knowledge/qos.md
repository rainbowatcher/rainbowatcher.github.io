## 要点

- QoS 不增加带宽，只决定拥塞时**谁先出队、谁被丢**；链路空闲时它不产生任何收益。
- 实际部署的是 DiffServ：边缘分类并写 DSCP，核心只信任标记做排队，不逐跳重新分类。
- 严格优先队列（LLQ）必须配带宽上限（通常 ≤ 链路 33%），否则语音队列一拥塞，其余流量直接饿死。
- 四个指标里语音只看时延、抖动、丢包，带宽需求反而只有几十 kbps；下载只在乎带宽。

## 机制

一条流量从入队到出队按顺序经过六步，前两步只在边缘做一次：

1. **分类**：按五元组、端口、应用识别、用户组判断流量类别。
2. **标记**：写入 L3 的 DSCP（IPv4 ToS 前 6 位）、L2 的 802.1p CoS 或 MPLS EXP。
3. **限速**：超速流量 policing 直接丢，shaping 缓存起来延迟发送，前者省内存、后者不丢包但增加时延。
4. **排队**：按标记进不同队列（LLQ、CBWFQ、WFQ）。
5. **调度**：出队顺序由严格优先或加权轮询决定。
6. **拥塞避免**：WRED 提前丢低优先级报文，避免队列满后全局同步性丢包。

优先级的可信边界（trust boundary）在接入交换机或 CE 路由器：用户侧报文可以被随意改写标记，所以边缘要么重新分类，要么对来自用户口的 DSCP 一律重置。

## 规则与取值

标准 PHB（Per-Hop Behavior）与常见映射：

| DSCP      | 名称                 | 典型用途               | 队列行为             |
| --------- | -------------------- | ---------------------- | -------------------- |
| EF (46)   | Expedited Forwarding | 语音 RTP               | 严格优先，低时延抖动 |
| AF41 (34) | Assured Forwarding   | 视频会议               | 高权重，超速降级     |
| AF31 (26) | —                    | 关键业务数据           | 中高权重             |
| AF21 (18) | —                    | 事务型业务（ERP、SAP） | 中                   |
| CS1 (8)   | Scavenger            | 备份、P2P              | 最低，带宽受限       |
| 0         | Default              | 普通上网               | 默认队列             |

排队与限速手段的取舍：

| 手段           | 作用                         | 代价                             |
| -------------- | ---------------------------- | -------------------------------- |
| LLQ 严格优先   | 语音零排队                   | 不限速就饿死其他队列             |
| CBWFQ 保证带宽 | 每类保底速率，剩余按权重分配 | 配置与链路速率绑定，改链路要重算 |
| policing 丢包  | 立即压住突发                 | 丢包导致重传，TCP 吞吐崩塌       |
| shaping 缓存   | 不丢包，平滑成整形速率       | 增加时延与内存占用               |
| WRED           | 拥塞前按标记提前丢           | 参数难调，配合 ECN 才不误伤      |

三种服务模型的分工：

| 模型           | 思路               | 现状                         |
| -------------- | ------------------ | ---------------------------- |
| Best Effort    | 不区分，尽力转发   | 无 QoS 的默认状态            |
| IntServ + RSVP | 每个流预约资源     | 状态量随流数线性增长，难扩展 |
| DiffServ       | 按标记聚合分类处理 | 现网主流                     |

## 示例

Linux 上用 `tc` 查看与配置出口队列，用 iptables 打标记。以下命令未在本机验证，需在 Linux 上执行：

```bash
# 查看网卡当前的队列规则与各类统计
tc -s qdisc show dev eth0

# 查看已有 DSCP 标记的过滤规则
tc filter show dev eth0 egress

# 给本机发出的 ICMP 打 EF 标记（测试用）
sudo iptables -t mangle -A OUTPUT -p icmp -j DSCP --set-dscp-class EF

# 观察出口报文头里的 DSCP 值（应为 0x2e = EF 46）
sudo tcpdump -ni eth0 -v icmp
```

正例与反例的差别在于标记是否落到**拥塞的那一跳**：只在本地 OUTPUT 链打标记，若中间路由器重置或隧道封装不保留 DSCP，到瓶颈处已退回 0，`tcpdump` 能看到值但队列行为不生效。

## 与相邻概念的区别

| 概念           | 差别                                                      |
| -------------- | --------------------------------------------------------- |
| TCP 拥塞控制   | 端到端各自退让，靠丢包和 RTT 反馈；QoS 在设备内部按类分配 |
| CoS（802.1p）  | L2 标记，3 位，只在单跳二层域内有效；DSCP 是 L3，可跨路由 |
| 带宽保证/限速  | 只约束速率上限，不决定拥塞时的先后；QoS 管的是排队顺序    |
| 流量整形与 QoS | shaping 是 QoS 的一个环节，只回答“发多快”，不回答“谁先发” |

## 边界

- 加密成为主流后（TLS 1.3 的 ECH、QUIC），只能靠 SNI、IP、端口或行为特征分类，精度下降；按应用 ID 与用户组的策略比按 DSCP 更可靠。
- IPsec/GRE 隧道两端要显式配置 DSCP 复制，否则外层头标记丢失或按 tunnel mode 被清零。
- 跨运营商链路上的标记不可信，通常只在本域内生效。
- 无线侧 Wi-Fi 有 WMM 的 AC_VO / AC_VI / AC_BE / AC_BK 四个接入类别，需与有线侧 DSCP 做映射，否则端到端优先级断裂。
- 语音质量的上限由最后一公里和抖动缓冲决定，QoS 只能保住队列里不排队，救不回已经拥塞的物理链路。
