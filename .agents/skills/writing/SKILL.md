# 知识库写作

## 何时必须使用

- 写入 `content/` 下任何 markdown 之前：新建、改正文、改 frontmatter、加站内引用、`git mv` 晋升。
- 判断一篇该进 `explore/`、`experience/` 还是 `knowledge/`。
- 只读代码、不改 `content/` 时不必读。

## 阶段

| 目录                  | 阶段         | 可以写                                       | 晋升条件                           |
| --------------------- | ------------ | -------------------------------------------- | ---------------------------------- |
| `content/explore/`    | 探索（草稿） | 本机实测、未验证判断、并列方案、待验证清单    | 真实执行过一次，能收敛出结论      |
| `content/experience/` | 经验         | 本机验证过的结论、命令、环境、失败路径        | 脱离本机仍成立，且能与别的经验合并 |
| `content/knowledge/`  | 知识         | 可复用结论、用法、边界                       | 终态                               |

- 晋升：`git mv content/<旧>/<slug>.md content/<新>/<slug>.md`，删掉过程段落，`date` 改成晋升日。
- 默认落库：写作一律落 `content/`，按上表选目录；不写仓库根、`docs/` 等别处，也不反问放哪。阶段不明先落 `explore/`，验证或收敛后再 `git mv` 晋升。
- 不在阶段表里的集合按性质直接落：第一人称过程 → `posts/`，永不发布 → `hide/`。
- 证据不搬家：知识引用经验、经验引用探索，不复制它们的段落。
- 结论失效：文首写「已失效（YYYY-MM-DD）」并链到替代文章，不删文——agent 需要知道这条路是错的。

## 写作

冲突时按序号取舍：

1. 一篇只覆盖一个主题。标题提取「技术对象 + 任务、机制或场景」，保留工具名与关键术语；不复述用户问句，不用「是什么」「怎么用」「如何」「为什么」「浅谈」「详解」「入门」。例：「atop 是什么，怎么用」应写成「atop 系统监控与历史回放」。
2. 去掉 frontmatter 后，正文前 5 行交代覆盖范围与结论：一句话 + ≤3 条要点，清单型写分类依据与查找方式；读完这段可以不读正文。调研草稿先给当前方向，后面的「当前判断」只展开依据与缺口。
3. 能引用就不复述：一条命令、一个版本号、一个结论只存在一处，其余位置给链接。
4. 段落 = 断言 + 依据；没有依据就写 `未验证`。
5. 表格优于长段，命令优于描述；命令要能直接粘贴，不写 `...`。
6. 行数预算：explore 实测类 ≤ 300、调研草稿 ≤ 40、experience ≤ 120、knowledge 叙论型 ≤ 200；清单型按条目算，每条 ≤ 8 行，整篇超 200 行就按类别拆篇互链。
7. 环境只写一处（系统 / 版本 / 日期）；knowledge 通常不需要环境。
8. 不写导语与总结段，不复述输出全文，不贴长日志（贴命令或路径）。

## frontmatter

| 集合       | 必填                              | 可选                  |
| ---------- | --------------------------------- | --------------------- |
| explore    | `title` `date` `tags`             | `subtitle` `description` |
| experience | `title` `date` `tags`             | `summary` `subtitle`  |
| knowledge  | `title` `date` `tags` `section`   | `subtitle` `updated`  |

- `date`：当前阶段的成稿日，`YYYY-MM-DD`，不加引号。
- `tags`：行内数组，复用已有标签，不塞整条问题或摘要关键词。
- `section`：只能是 `基础` / `语言` / `系统` / `工具`（`app/utils/knowledge.ts`）。
- 摘要字段决定 agent 要不要打开正文，只有一处：explore / knowledge 用 `subtitle`，experience 用 `summary`；写技术对象、结论或验证状态与适用前提，不复述标题，不写「本文介绍」。
- `posts/`、`hide/` 的必填字段见 `scripts/check-content.mjs`，本表不管。

## 小节

同一阶段用同一组 H2，agent 靠标题切片；explore 按两类固定写法，knowledge 按骨架选 H2，但首屏与来源位置固定。额外内容放在这组之后。

- explore 本机实测：`## 结论先行`
- explore 调研草稿：`## 问题` `## 候选` `## 当前判断` `## 下一步` `## 参考`
- experience：`## 结论` `## 环境` `## 做法` `## 边界与失败` `## 证据`
- knowledge：按骨架走（见下），但首屏 3-5 行与 `## 参考` 不变。
- H2 只做切片键，不承担检索关键词；具体主题与术语放 `title`、H3、表格行与正文。

### 知识骨架

技术知识不同类，知识文章按主体选一份骨架，不硬塞进同一套 H2：

| 类型    | 何时用                     | 骨架                               |
| ----- | ----------------------- | -------------------------------- |
| 工具与命令 | 命令用法、参数、输出解读，含单工具与多命令合集 | `templates/knowledge/cli.md`     |
| 概念与机制 | 原理、协议、触发时机、匹配规则、优先级     | `templates/knowledge/concept.md` |
| 清单与目录 | 标签、注解、API、资源链接等成组条目     | `templates/knowledge/catalog.md` |
| 操作流程  | 安装、配置、迁移的步骤、验证与回滚       | `templates/knowledge/howto.md`   |

- 一篇只用一个骨架；混合内容按主体选，其余引用别篇。
- 骨架里的 H2 可增删，条件是不丢首屏、`## 参考` 与可检索的术语密度。
- 都不合适时用最接近的一份，不为单篇新造结构。

## 引用

- 站内写相对 `.md` 链接：`[Linux 简介](../knowledge/linux-intro.md)`。渲染时转成路由，`pnpm content:check` 校验文件存在。
- 链接文字用目标标题，不写「这里」「上文」「另一篇」。
- 站外只引官方文档、源码、issue；二手博客只作草稿阶段的线索，并注明来源性质。
- 引用前确认目标还在：`ls content/<集合>/`。

## 读写顺序

- 读：`title` + 摘要（explore / knowledge 看 `subtitle`，experience 看 `summary`）→ 首屏 5 行 → 结论、当前判断与边界 → 引用。四步够用就不读全文。
- 写：查重 `rg -l "<关键词>" content/{explore,experience,knowledge}` → 选阶段 → knowledge 再选骨架 → 套模板并替换全部占位符（不留假日期、假链接、空表格）→ `pnpm content:check`。
- 命中已有文章就改那一篇，不新建。

## 边界

- 阶段表只管 `explore/` / `experience/` / `knowledge/`；`posts/` / `hide/` 不适用阶段，但仍受「写作」「引用」两节约束。
- 不管页面、样式与渲染；正文只用 GFM 与已注册的 MDC 组件。
- 旧文不批量改写；下次改到哪篇，再把它对齐到最近的一组小节。
