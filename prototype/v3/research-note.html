hc 父子终端：命令行之外的入口

从 JSON-RPC 的 caller 字段，到 Sheprd GUI、mods、automations 各自能建出什么。

2026-11-10 HerdrCLITerminal
本机环境依赖，引用前请复验

研究内容基于当时的机器状态、工具版本与本地配置：macOS、hc 0.1.19（PATH）与 bundle 内 0.1.13、herdr 0.9.5、Sheprd 20261104.1。换台机器未必复现，文中的命令与数据须在本机重新跑过再引用，不能当通用结论使用。

结论先行 #

  • 父子关系不是 hc run 的参数，而是 terminal.run 这个 JSON-RPC 方法的字段：parent / caller / no_parent / outlive_parent。CLI 只是其中一种把字段填好的方式。
  • 唯一自动认父的机制是 caller（CLI 里由 $HC_TERMINAL_ID 填入）。同一个方法不传 caller，建出来的终端 parent 就是 null：父子靠客户端自报，核心不会猜。
  • 命令行之外真正能建出父子链的只有一条路：自己说这套协议（unix socket、hc connect 的 stdio、ssh box hc connect）。不需要 hc 可执行文件，也不需要是终端里的子进程。
  • Sheprd GUI 能建终端，但本机上 20 个 hc 终端全部 parent: null。GUI 用的是标签与版面模型，和 hc 的父子是两套东西。
  • herdr 1（0.9.5）的 128 个请求方法里，parent 命中 0 次；pane 列表是 pane_id / tab_id / workspace_id / terminal_id 平铺。

判定方法 #

分三步，每一步都留了可复现的命令：

  1. 读协议：hc schema（OpenRPC）看字段，herdr api schema --json 看 herdr 1 有什么。
  2. 绕过 CLI 直接调：向 $HC_TERMINAL_SOCKET 发新行分隔的 JSON-RPC，用 hc get 核对结果。
  3. 看现状：hc ls --all --json 与 hc get 对比谁建的终端带 parent。

一、父子的载体是协议字段 #

hc schema 里 terminal.run 的参数字段（摘）：

字段 语义 缺省
caller 谁在调用（终端里就是 HC_TERMINAL_ID） 空
parent 父终端；空则取「被启动时所在的终端」 空
no_parent 就算从终端里启动也不给父 false
outlive_parent 父程序结束也留着它 false
die_with_parent 请求里传 true 没用，真正的开关是 outlive_parent false

五组实测 #

  • 只给 argv、不给 caller：parent: null，cwd 成了核心的 /。
  • 给 caller: "t1f"：parent: "t1f"，die_with_parent: true。
  • 再加 outlive_parent：parent 不变，die_with_parent 变 false。
  • parent 指向不存在的终端：报错 not_found，不建。
  • caller、no_parent、parent 同传：parent 生效，显式认父赢。

最后一条值得记：no_parent 只是压掉默认值，显式 parent 赢。所以「我要游离」和「我要认父」同时说时，认父生效。

二、途径一：直接说协议 #

unix socket #

不用 hc，标准库就够。新行分隔的 JSON-RPC，一问一答：

python 
import json, os, socket

s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.connect(os.environ["HC_TERMINAL_SOCKET"])
req = {
    "jsonrpc": "2.0", "id": 9, "method": "terminal.run",
    "params": {"argv": ["/bin/sh", "-c", "sleep 600"], "name": "sock-child", "caller": "t1f"},
}
s.sendall((json.dumps(req) + "\n").encode())
print(s.recv(65536))

回报里就是 {"address": "t26", "name": "sock-child", "parent": "t1f", "die_with_parent": true}。这条路径的意义是：任何进程都能建父子，只要它知道地址；编辑器插件、CI 脚本、面板程序不必 fork 一个 hc，也不必身处终端。

代价 #

  • 客户端自己负责地址管理：parent 不存在会被 not_found 拒绝，没有「自动找最近终端」这种便利。
  • 不传 cwd 时子终端落在核心的 cwd（实测 /），不是调用者的 cwd。CLI 帮你填了，裸协议没有。

三、途径二：环境变量继承 #

hc 给每个终端都注入 $HC_TERMINAL_ID 与 $HC_TERMINAL_SOCKET。凡是在终端里跑起来的东西，比如 npm script、make 目标、编辑器 task，只要它调 hc run，不需要任何参数就自动成父。反过来把变量抹掉，同一台机器、同一个 CLI、同一秒，结果从认父变成游离。

sh 
hc run --bg --name envprobe /bin/sh -c 'echo "id=$HC_TERMINAL_ID" > /tmp/envprobe.txt; sleep 30'
cat /tmp/envprobe.txt

env -u HC_TERMINAL_ID hc run --bg --name noparent-cli /bin/sh -c "sleep 600"
hc get noparent-cli --json

五、Sheprd GUI：能建终端，但不建父子 #

GUI 侧和终端有关的命令一望即知：new_tab、split_right、split_down、new_workspace、new_window。这些既能按快捷键触发，也能被 mod 的 herdr.run("split_down") 触发。看现状：

终端 创建时间 parent 标签
t10 11-09 13:17 null herdr.space / herdr.tab / where
t1y 11-10 11:11 null 同上
t20 11-10 15:24 null 同上

结论：GUI 建的是「标签里的终端」，是 hc 模型里的游离节点；分屏、tab 都是版面关系，落在 herdr.space / herdr.tab 上，不落在 parent 上。想让 GUI 里的终端进入 hc 的树，只有一招：在那个终端里跑 hc run。

这一段是观察证据，不是受控实验

翻转 herdr_2_terminals 做 A/B 会改动窗口与会话，没有做。bundle 里的 herdr-core 是 hc 0.1.13，PATH 上是 0.1.19，两个客户端对着同一个 socket，理论上也可能有行为差异，没验证。

八、没验证的，和踩到的坑 #

没验证：跨机器的父（hc machine ls 是空的）、GUI 的 A/B、hc connect --session 指向另一个核心时父引用是否有效。

踩到的坑，与命令行无关，但都会让「父子」看起来不对：

  • 裸协议不填 cwd，子终端落在核心的 cwd，不是调用者目录。
  • parent 写错不会被宽容处理：not_found，直接失败。
  • no_parent 不覆盖显式 parent，两者同传时是认父。
  • hc ls --all --json 不给 die_with_parent 与 labels。

九、复现与清理 #

sh 
hc ls --all --json | python3 -c 'import json,sys; [print(t["address"], t.get("parent")) for t in json.load(sys.stdin)["terminals"]]'

env -u HC_TERMINAL_ID hc run --bg --name probe2 /bin/sh -c "sleep 600"

for t in probe probe2; do hc kill "$t"; hc rm "$t"; done
